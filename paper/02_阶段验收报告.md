与 100 个测试计算图，形成《评估器机制说明》（`paper/01_评估器机制说明.md`），
逐条回答了 A–Q 共 17 个问题：图数据结构、DAG 构成、可切分节点、COPY 不可
切分的原因、`node_to_subgraph` / `core_schedules` 语义、Task 恢复规则、

三个问题的 Task 结构、Makespan 决定因素、`added_copy_bytes` 组成、
Cache 命中率定义、硬约束清单、软目标清单。

**【新增代码】**
`solution/npu/paths.py`（路径与官方配置唯一来源）、
`solution/npu/graphlib.py`（图解析、COPY 收缩、搬运量解析模型）、
`solution/npu/features.py`（五类图特征提取与缓存）、
`solution/run_singlecore.py`（官方单核基准批量预计算）。

**【实验结果】**
* 100 个用例的官方单核基准全部算出（`results/singlecore_baseline.json`），
  Makespan 从 $1.89\times10^4$ 到 $6.38\times10^7$，中位数 $4.91\times10^5$；
* 40/100 个用例的单核基准已经产生换入换出，最大 $2.77\times10^8$ 字节；
* 特征统计见《论文》§2.3 表。

**【发现的问题】**
1. **文档与代码不一致**：`docs/多核并行模拟执行算法.md` 第 4 节给出的
   DDR 结算含 $n/(n-1)$ 的"加入惩罚"因子，该因子只出现在
   `schedule_step3.reschedule_ddr_ends`（核内定序阶段），三个**多核**
   评估器的 `reschedule_ddr` 是**纯公平共享**。最终 Makespan 由多核评估器
   给出，故建模采用纯公平共享。
2. **`op` 名称不做白名单校验**，Pipe 完全取自 `pipe` 字段；因此不能按算子
   名推断执行单元。
3. **`_copy_traffic_bytes` 的口径**：`COPY_IN` 计其输出张量、`COPY_OUT` 计其
   输入张量，两端都是**片上**张量的大小，而非 DDR 侧张量。
4. Step2 生成的 spill 节点 `cycles = max(1, size//64)` 与真实执行时长
   `⌈size/bw⌉` 不一致；真实时长由 `_op_duration` 重算，故该字段不影响成绩。

**【下一步】** 建立统一数学抽象并实现基线。

**【是否可复现】** 是。`python solution/run_singlecore.py --jobs 16` 重算全部基准；
特征缓存于 `results/cache/features`，删除后自动重建。

## 阶段 2：统一数学抽象与可行性构造

**【完成内容】**
把三个问题统一建模为带通信代价的有向无环图划分与调度：决策变量
$x_v$（子图）、$y_s$（核心）、$\pi_k$（同核顺序）；约束 (C1)–(C9)；
目标 $\min \mathrm{MK}$，搜索内部使用解析代理 $F$。
证明了**引理 1（可行性构造）**与**引理 2（同层独立性）**：取子图为
$(c,r)$ 等价类即可让 (C1)–(C5) 五类硬约束自动成立，且同一同步层次内无跨核边。

**【新增代码】**
`solution/npu/partition.py`（亲和原子化、SCC 合并、$\sigma$ 线性扩展、
连续区间分块、受可达性约束的块合并）、
`solution/npu/assign.py`（场景 A 的 Task 级事件模拟、场景 B 的 Pipe 负载模型、
LPT 与移动式局部搜索）、
`solution/npu/stratify.py`（跨核同步层次与 (核心, 层次) 子图成形）。

**【实验结果】**
在 case_001、case_004、case_008、case_013 上，"按弱连通分量装箱 + 每核 1 个子图"
即可得到 $N=4$ 时 3.77–3.96 的加速比，验证了"先按连通结构分核"的第一性策略。

**【发现的问题】**
**块级依赖必须取自收缩 COPY 后的算子 DAG，而不是张量生产/消费关系。**
形如 `op → COPY_OUT → DDR → COPY_IN → op` 的依赖在张量关系上断开，
早期实现据此判定"合并安全"，结果被官方评估器以
`contracted subgraph graph contains a cycle` 拒绝（case_003、问题 1）。
已在 `partition.BlockSet._compute_edges` 改用 `g.succs` 修正。

**【下一步】** 实现基线与主算法，并用官方评估器对比。

**【是否可复现】** 是。

## 阶段 3：基线、主算法与关键诊断

**【完成内容】**
实现 5 个基线（随机、拓扑等分、负载均衡、通信聚类、整图单核）与主算法
CAP-LS 的四个阶段，全部通过官方评估器打分。

**【新增代码】**
`solution/npu/algorithms.py`（`TrafficState` 增量代价、`_local_search`、
`cap_ls`、候选参数网格）、`solution/npu/evaluate.py`（官方评估器封装与
方案哈希级缓存）、`solution/npu/experiment.py`、`solution/run_experiments.py`、
`solution/solve.py`。

**【实验结果（诊断性，$N=4$）】**

| 用例 | 结构 | 初版 CAP-LS | 加入同步层次分层后 |
|---|---|---|---|
| case_062（问题 1） | 2181 条独立链 + 归约树 | 1.00 | **3.95** |
| case_062（问题 2） | 同上 | 1.07 | **3.97** |
| case_003（问题 1） | 单主分量、深度 305 | 不可行（成环） | **2.63** |
| case_005（问题 2） | 单连通、深度 138 | 1.48 | **1.85** |
| case_016（问题 2） | 305 级体同步链 | 0.99 | **1.26**（需超细粒度） |

**【发现的问题（本项目最重要的发现）】**
`schedule_step3.issue_step` 对"申请片上张量的算子"施加**全局申请序**，
只有队首者可发射。于是核内序列前部的跨核 `COPY_IN` 会让整个核心停摆。
case_062、$N=4$ 的诊断：某核心 `PIPE_M` 净忙碌 $6.55\times10^5$ cycle，
跨度 $2.14\times10^6$ cycle，其中两段空转各约 $7.12\times10^5$ cycle
（占空转总量 96%），而配置中的跨核延迟仅 500 cycle。
→ 直接导致引入跨核同步层次 $r(v)$ 与 $(c,r)$ 子图成形。

次要问题：
* 局部搜索代价随块数线性增长，`block_cap=0.08` 时单候选求解时间达 8 s。
  已通过"只考察计算量最大的 260 个块 + 移动次数上限 2200"降到 1 s 量级。
* 方案文件名曾使用 `*` 作为变体标记，在 Windows 上非法；已改为 `_best`。

**【下一步】** 全量实验：主结果、基线、消融、粒度与硬件敏感性。

**【是否可复现】** 是。`python solution/solve.py <graph> --problem p --cores n`
可复现任一单用例结果，并与官方 CLI 的输出逐位一致（已在 case_019 上核对：
求解器内部报告 27 333，官方 CLI 报告 27 333）。

基线对比（$N=4$ 几何平均）：随机 0.91/1.08/1.09、拓扑等分 1.06/1.68/1.70、
负载均衡 1.07/1.51/1.53、通信聚类 2.05/2.51/2.56，CAP-LS 2.91/3.12/3.19；
五种算法在 100 用例 × 3 问题 × 4 核数上**均无不可行方案**。

**【发现的问题】**

1. **消融给出一条负面结论**：在单配置设定下，"LPT 装箱 + 局部搜索"平均**不如**
   朴素轮转分核（问题 1 −2.3%、问题 2 −3.6%、问题 3 −3.0%）。
   进一步拆开看，失分来自 LPT 本身而非局部搜索（去掉局部搜索几乎无变化）。
   已在论文 §11.1 如实报告并给出解释，同时说明这正是把两者都作为多起点候选的理由。
2. **同步深度代价项贡献几乎为零**（−0.5% / −0.0% / −0.2%）——它只在少数链状用例上有用。
3. **L2 容量与带宽已经饱和**：在 64 KB–16 MB 与 60–1000 B/cycle 的范围内，
   Makespan 变化不超过 0.2%。瓶颈在计算图能提供多少可共享复读，而不在 L2 规格。
4. **`solution/validate_model.py` 的场景 A 代理最初写错**：它按子图 id 升序模拟 Task 激活，
   但 `canonical_plan` 会把子图 id 按"核分组"重编号，升序不再是拓扑序，
   导致 219/480 条 P1 记录抛 KeyError。已改为按"每核队首 + 前驱全完成"的真实激活规则推进。
   该缺陷只影响论文 §10.7 的检验脚本，**不影响任何上报成绩**（成绩全部来自官方评估器）。
5. 一个 `granularity` 任务耗时异常（单任务 23 525 s），因为 $\beta=2.0$ 在最大用例上
   产生了近乎整图的单个 Task，触发了官方 Step2/Step3 的最坏情形。

**【是否可复现】** 是。`bash solution/run_all.sh 16 && bash solution/finalize.sh`
可从零复现全部数字、图表与论文。已抽查 3 个用例 × 3 个问题，
