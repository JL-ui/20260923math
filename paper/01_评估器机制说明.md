## A. 原始计算图的数据结构

顶层 JSON 含三个数组（`validate_graph`）：

| 字段 | 元素字段 | 约束（代码强制） |
|---|---|---|
| `tensors` | `id, pos, size` | `pos ∈ {DDR, L1, UB}`；`size` 为非负整数 |
| `ops` | `id, op, pipe, cycles` | `pipe ∈ {PIPE_MTE2, PIPE_MTE3, PIPE_M, PIPE_V}`；`cycles` 非负整数；**`op` 名称不做白名单校验** |
| `edges` | `source, target` | 端点必须存在；禁止 tensor→tensor 边；禁止重复边 |

op 与 tensor **共享同一个 id 空间且全局唯一**（`ids` 集合同时收纳两类节点）。
`check_acyclic` 对"含 COPY 节点的完整图"做 Kahn 判环。

**实测数据规模**（100 个用例）：可切分算子数 552–35 705（中位 3 720），
张量数 599–40 287，DAG 深度 3–2 440，平均宽度 4.7–3 110。

## B. Tensor、Op、Edge 如何构成 DAG

边集只允许 `T×O ∪ O×T`（二部图）。评估器在三处把二部图**收缩**成算子级 DAG：

1. `schedule_step1.bipartite_to_op_adj`：`producer(t) → consumer(t)`；
2. `schedule_step3._build_graph_views`：同上，并额外解析直接 op→op 边；
3. `stub_multicore_cut_and_schedule._build_op_adjacency` +
   `_contract_excluded_copy_nodes`：在 1 的基础上**跳过 COPY 节点**，
   保留其两侧最近可切分算子之间的可达性。

第 3 条是选手方案合法性判定所用的依赖关系，因此本文的数学模型采用同一定义：

$$E_{\mathrm{op}}=\{(u,v)\mid u,v\in V_{\mathrm{op}},\ \exists\ u\rightsquigarrow v\ \text{且中间只经过 COPY 节点}\}.$$

> **实现细节（易错点）**：形如
> `op → COPY_OUT → DDR tensor → COPY_IN → op` 的依赖在"张量生产者/消费者"
> 关系上是**断开**的，但经 COPY 收缩后依然是一条算子依赖边。求解器若只用
> 张量关系建图，会漏掉这类边，导致自查"无环"而评估器报
> `contracted subgraph graph contains a cycle`。本项目在
> `partition.BlockSet._compute_edges` 中显式改用收缩后的算子 DAG。

## C. 哪些 Op 可以被切图

`EXCLUDED_COPY_TYPES = {'COPY_IN','COPY_OUT'}`。
`derive_multicore_plan` 要求

```python
set(node_to_subgraph) == {op.id | op.op ∉ EXCLUDED_COPY_TYPES}
```

**恰好相等**——少一个报 `missing`，多一个报 `extra`。

## D. 为什么 COPY_IN / COPY_OUT 不能作为切图对象

因为评估器会把原图中的 COPY 节点**整体丢弃并重建**：

* 问题 1 `_build_scene_a_tasks`：子图的局部图只装入
  `nodes_by_subgraph[task_id]`（全是非 COPY 算子），随后按边界规则新建
  `COPY_IN/COPY_OUT` 与配套 DDR 张量；
* 问题 2/3 `_build_scene_b_tasks`：同理，只为"图输入、图输出、跨核边"
  新建 COPY 对。

原 COPY 节点在 Task 中不存在，其搬运量只作为**基准值**
`original_graph_copy_bytes` 参与"额外搬运量"的减法。若允许选手给 COPY 节点
指定子图，就会与自动重建规则冲突、并二次计入搬运量。

## E. `node_to_subgraph` 的语义

`{十进制字符串或整数 op id : 非负整数 sgid}`。键必须是 ASCII 十进制
（`node_id.isascii() and node_id.isdecimal()`），不同文本键若转成同一整数按重复处理。
值必须是 `int` 且非负（`bool` 被显式排除）。语义 = 可切分算子集合上的一个**划分**。

## F. `core_schedules` 的语义

二维整数数组，外层下标即核心 id，`num_cores = len(core_schedules)`。
全部内层数组合并后每个 sgid 恰好出现一次；内层数组为该核上的**子图执行顺序**。
内层数组允许为空（该核空闲）。

## G. evaluator 如何从切图结果恢复 Task

| 问题 | Task 定义 | 构造函数 |
|---|---|---|
| 1 | **一个子图 = 一个 Task** | `_build_scene_a_tasks` |
| 2、3 | **一个核心 = 一个 Task**（该核全部子图合并） | `_build_scene_b_tasks` |

问题 2/3 中，核内算子序由 `_prioritize_task_seq` 决定：先用
`step1_schedule` 得到局部图的拓扑序 `raw_seq`，再**按子图在
`core_schedules[k]` 中的名次做稳定排序**，最后用 `_check_topo` 校验重排后
仍满足局部依赖。也就是说：

$$\text{核内执行序}=\text{按子图名次分桶}\ \oplus\ \text{桶内保持 Step1 顺序}.$$

这一点至关重要：**同核子图顺序不仅决定依赖等待，还直接决定核内算子的物理执行序**。

## H. evaluator 如何自动插入跨子图搬运

### 问题 1（场景 A）

对每个子图 $S$ 与它触及的每个张量 $t$（记可切分生产者集 $P_t$、消费者集 $C_t$）：

* **输入边界**：$C_t\cap S\neq\varnothing$ 且 $P_t\cap S=\varnothing$
  → 新建 DDR 张量 + `COPY_IN`（`PIPE_MTE2`，`cycles=⌈s_t/\mathrm{bw}⌉`）；
* **输出边界**：$P_t\cap S\neq\varnothing$ 且
  （$t$ 被原始 `COPY_OUT` 消费 **或** $C_t=\varnothing$ **或** $C_t\setminus S\neq\varnothing$）
  → 新建 DDR 张量 + `COPY_OUT`（`PIPE_MTE3`）。

注意：**同一核上相邻的两个子图之间也必须经 DDR 中转**——这是场景 A 的定义。
另外，Task 内的原 DDR 张量会被改写成 `pos='UB'`（`tensor['pos']='UB'`），
原 DDR 张量只以"边界副本"的形式出现。

### 问题 2/3（场景 B）

按张量遍历（`for tensor_id in sorted(tensor_by_id)`）：

* **图输入**（$P_t=\varnothing$）：**每个消费核各 `COPY_IN` 一次**；
* **图输出**：每个生产核各 `COPY_OUT` 一次；
* **跨核**：对每个 $(\text{src core},\text{dst core})$ 组合新建
  一对 `COPY_OUT`/`COPY_IN`，**共享同一个 DDR 张量 id**，并登记为
  `cross_links`（这是唯一带 `cross_core_copy_delay_cycles` 的依赖）。

COPY 被挂到哪个子图也有确定规则：`COPY_IN` 挂到该核**名次最小**的消费子图，
`COPY_OUT` 挂到该核**名次最大**的生产子图。

> **由此得到一条关键推论**：场景 B 中**同一核内的子图边界完全不产生搬运**，
> 子图划分在核内只剩"执行顺序"这一个作用。

## I. evaluator 如何处理 L1/UB 容量不足

两道防线：

1. **Step2（`step2_spill_insertion`）**：沿 Step1 序模拟驻留量，
   在"alloc → 容量检查 → execute → free"的时序下，一旦某类容量超限就按
   **Belady（最远下次使用）** 选牺牲者，插入 `COPY_OUT`(spill‑out) +
   `COPY_IN`(spill‑in)，并对该逻辑张量做**版本重命名**（incarnation）。
   同一逻辑张量最多写回 DDR 一次，其后只生成 `COPY_IN`
   （`spill_out_copies_data` 标志）。若当前 op 正在使用的张量占满容量而无可换出者，
   抛 `Step2SchedulingError`——**这是一条硬约束**。
   注意 spill 节点的 `cycles` 写成 `max(1, size//64)`，但真正执行时长由
   `_op_duration` 按 `⌈size/\mathrm{bw}⌉` 重算，故此字段不影响成绩。
2. **Step3（`step3_simulation`）**：用"可拆分虚拟额度"再次门控。
   释放张量时把容量退回 `free_credits`；新 producer 取用额度时，对额度的
   **全部来源读者**补一条 `op→op` 的 `MEMORY_REUSE` 边（WAR/WAW），
   写进 `execution_graph`。多核模拟把这些边当作普通依赖。

## J. evaluator 如何模拟共享 DDR 带宽

全局一个 `ddr_remaining_work` 池（**所有核心共享**）。`remaining_work` 的单位是
"独占全部带宽时还需的 cycle"。$n$ 个在途搬运时每个的推进速度为 $1/n$；
每当有搬运加入/完成，先按旧并发数结算，再把剩余工作量排序、逐层推算结束时刻：

$$\Delta t_i=(w_i-w_{i-1})\,(n-i+1),\qquad \text{end}_i=\Big\lceil t_0+\sum_{j\le i}\Delta t_j\Big\rceil .$$

只有**端点含 DDR 张量**的 COPY 才进池（`_uses_ddr_bandwidth`）。

> **与文档的差异（已核对）**：`schedule_step3.reschedule_ddr_ends` 里额外带一个
> $n/(n-1)$ 的"加入惩罚"因子，而三个**多核**评估器里的 `reschedule_ddr`
> **没有**该因子，是纯公平共享。由于最终 Makespan 只由多核评估器给出，
> 本文建模采用纯公平共享。

## K. evaluator 如何处理 Pipe 并行

* 每核 4 条 Pipe，`PIPE_SLOTS = 1` ⇒ 同一 Pipe 同时只有 1 条在飞指令；
* 每条 Pipe 的**发射顺序被 Step3 固定**：
  `planned_pipe_orders[pipe] = seq_ext 在该 Pipe 上的投影`，
  多核阶段用 `pipe_cursor` 严格按此顺序放行（`queue_if_ready` 里
  `order[cursor] != op_id` 则不入队）。

> **最关键的隐含约束（本项目的核心发现）**：Step3 的 `issue_step` 中，
> 凡"会申请片上张量"的算子都不进普通队列，而是排进全局
> `allocation_order`（即 `seq_ext` 的投影），且**只有队首者可以发射**：
>
> ```python
> candidate = allocation_order[next_allocation_rank]
> if candidate in allocation_ready and candidate_pipe == pipe and can_allocate_outputs(candidate):
>     op_id = candidate        # 只有队首能发射
> ```
>
> 于是，一旦某个**跨核 `COPY_IN`** 排在核内序列的前部而数据尚未送达，
> **整个核心的四条 Pipe 全部停摆**。实测 case_062、N=4 时单核心因此产生了
> 两段各约 $7.1\times10^5$ cycle 的空转，占该核心跨度的 67%，
> 而配置里的跨核延迟只有 500 cycle。**跨核依赖的真实代价远大于名义同步延迟**，
> 这直接决定了本文"跨核同步层次分层"的设计。

## L. P1、P2、P3 的 Task 结构

* **P1**：Task = 子图。核心串行执行自己的 Task 列表，`core_active_task`
  保证同一时刻每核只有一个活跃 Task。激活条件（`task_release_time`）：

  $$\text{start}(T)\ \ge\ \max\Big(\text{prevEnd}(k)+W_{\text{same}},\ \max_{T'\in \mathrm{pred}(T),\,c(T')\ne k}\big(\text{end}(T')+W_{\text{cross}}\big)\Big)$$

  且**全部**前驱 Task 必须已完成。$W_{\text{same}}=100$、$W_{\text{cross}}=1000$。
* **P2/P3**：Task = 核心。所有核心的 Task 在 $t=0$ 一起参与调度，
  跨核依赖通过 `cross_links` 表达：目标 `COPY_IN` 最早释放时刻
  $=\text{end}(\text{COPY\_OUT})+500$。
* P3 在 P2 之上增加只读 FIFO Cache（见 O）。

## M. Makespan 最终由什么决定

* P1：`max(task_end.values())`；
* P2/P3：`max(op_end.values())`。

其下界为

$$\mathrm{MK}\ \ge\ \max\Big(\max_k\max_{p\in\text{Pipes}} L_{k,p},\ \frac{B_{\mathrm{DDR}}}{\mathrm{bw}},\ \mathrm{CP}\Big),$$

其中 $L_{k,p}$ 为核 $k$ 上 Pipe $p$ 的总占用、$B_{\mathrm{DDR}}$ 为全部 DDR 搬运字节、
$\mathrm{CP}$ 为关键路径。

## N. `added_copy_bytes` 如何产生

```python
partition_added = Σ_tasks copy_bytes(task_graph) − copy_bytes(original_graph)
spill_added     = Σ_spill  size × (1 + spill_out_copies_data)
added_copy_bytes = partition_added + spill_added
```

`copy_bytes` 的统计口径是：`COPY_IN` 计其**输出**张量大小、`COPY_OUT` 计其**输入**
张量大小（`_copy_traffic_bytes`）。因此三类新增搬运分别对应：
① 跨 Task 边界中转；② 多 Task 对同一输入的重复读取；③ 核内换入换出。

**实测**：官方单核基准中已有 40/100 个用例出现 spill（最大
$2.77\times10^8$ 字节），说明"整图单 Task"本身就受 L1/UB 容量之苦——
这正是多核切分可能取得**超线性加速**的原因。

## O. Cache 命中率如何定义

只有 `COPY_IN` 可查 Cache（`cache_eligible`）。键为
`tensor.get('logical_tid', tid)`，即该 `COPY_IN` 写入的**片上**张量的逻辑 id：

* 场景 B 中跨核/图输入 COPY_IN 写入的片上张量沿用**原图张量 id**，
  因此"同一张量被多个核心读入"天然共享同一个键；
* Step2 产生的 spill‑in 其 incarnation 带 `logical_tid`，
  因此**同一张量的多次换入**也共享同一个键。

命中走 `CACHE_READ` 带宽池（250 B/cycle，与 DDR 池相互独立），
未命中走 DDR 池并在**完成时**按 FIFO 写入 Cache（容量 1 MB，
单个张量超过容量则不缓存）。

$$\text{hit\_rate}=\frac{\text{hit\_bytes}}{\text{hit\_bytes}+\text{miss\_bytes}}\quad(\textbf{按字节}，非按次数).$$

## P. 哪些约束是"算法必须满足"的硬约束

1. `node_to_subgraph` 恰好覆盖全部非 COPY 算子，值为非负整数；
2. 每个子图恰好出现在一个核的调度列表中一次；
3. **子图商图无环**（`contracted subgraph graph contains a cycle`）；
4. **同核子图顺序不得违反子图依赖**（`dependency order violation on core k`）；
5. P1：子图依赖 + 同核 Task 串行顺序的**合并图无环**（`validate_task_order`）；
6. P2/P3：本地依赖 + Pipe FIFO + 跨核 COPY 的**全局操作图无环**（`validate_execution`）；
7. P2/P3：子图名次重排后仍满足核内依赖（`_prioritize_task_seq`）；
8. 核内容量可行：Step2 必须能找到换出牺牲者，Step3 虚拟额度不得耗尽；
9. 模拟必须能推进（无死锁、时间严格递增、不超 `max_iter`）。

## Q. 哪些指标只是优化目标而非硬约束

* **Makespan**（主指标）；
* **总额外数据搬运量**（次指标）；
* **Cache 命中率**（次指标，仅问题 3）；
* 负载均衡度、核内存储峰值、子图数量等——评估器只**报告**不**拒绝**。

## R. 本项目据此确立的可行性构造（保证 1–9 全部满足）

设 $\sigma$ 是算子级 DAG 的一个线性扩展，$c:V_{\mathrm{op}}\to\{0,\dots,N-1\}$
是核心分配，定义**跨核同步层次**

$$r(v)=\max_{u\to v}\big(r(u)+\mathbb 1[c(u)\ne c(v)]\big),\qquad r(v)=0\ \text{若}\ v\ \text{无前驱},$$

并取**子图 $=(c,r)$ 等价类**（必要时再按规模沿 $\sigma$ 切片）。则：

* $r$ 沿依赖边非降、跨核边严格 $+1$ ⇒ 按 $(r,c)$ 编号即为商图的一个拓扑序
  ⇒ 硬约束 3、4、5、6、7 自动成立；
* **同一层次内不存在跨核边**（否则终点层次 $\ge r+1$）⇒ 同层各核子图互相独立；
* 每个核上"需要远端数据"的算子被自动推迟到更高层次 ⇒ 核内先跑完全部本地
  就绪工作，最大程度规避 K 节所述的"申请序停摆"。

容量类硬约束 8 通过控制子图规模上界间接满足，并由官方评估器最终确认；
本项目所有上报结果均为官方评估器 `feasible=True` 的输出。
